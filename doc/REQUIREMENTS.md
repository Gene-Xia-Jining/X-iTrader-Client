# iTrader 智能交易系统需求

## 1. 项目目标

构建一个独立运行的 iTrader 智能交易系统。

客户端从交易策略服务器获取交易信号，并根据服务器给出的目标仓位，通过 TqSdk 调仓到目标手数。

客户端不负责交易策略计算，也不使用 TqSdk 订阅 K 线或计算指标。

---

## 2. 系统职责

客户端负责：

* 向服务器提交交易品种
* 接收服务器的新信号通知
* 根据服务器信号，通过 TqSdk 把持仓调到目标手数（开仓 / 平仓）
* 确认调仓真正成交后才记为成功（持仓到位）
* 记录交易信号执行状态
* 防止同一个交易信号重复执行
* 记录交易执行结果
* 查询并展示账户资金、持仓、委托、成交，并沉淀历史成交
* 管理客户端运行状态

客户端不负责：

* K 线策略计算
* 判断做多还是做空
* 修改服务器策略
* 根据自己的算法产生交易信号
* 用 TqSdk 订阅 K 线或计算指标

交易方向由服务器决定。

### TqSdk 的实际职责

* **交易执行**：`TargetPosTask` 以 ACTIVE 追价把持仓调到目标手数，持续推进
  `wait_update` 直到 `get_position` 确认到位；超时或拒单判失败并撤掉本次委托。
  主连（`KQ.m@` / `KQ.i@`）只能看行情，下单前换成 `underlying_symbol` 的实际合约。
* **账户数据**：读取资金 / 持仓 / 委托 / 成交，另有按账户常驻的监听会话推送快照；
  当日成交沉淀到本地 SQLite，支持跨交易日按时间区间查询。
* **行情元信息**（不驱动策略）：`quote.trading_time` 用于非交易时段门控，
  `quote.last_price` / `volume_multiple` 用于持仓估值与合约乘数，
  `quote.underlying_symbol` 用于主连换实际合约。
* **认证与连通**：`TqAuth` 登录快期权限账户、启动前交易网关预探测、
  `TqApi` 握手校验账户权限。

## 3. 技术栈

主要技术：

## 4. 核心业务流程

```text
Client
  │
  │ 提交交易品种
  ▼
Server
  │
  │ 产生交易信号
  ▼
Client 收到通知
  │
  │ 获取完整信号
  ▼
检查 SQLite
  │
  ├── 已执行 → 忽略
  │
  └── 未执行
          ↓
     检查是否在交易时段
          │
          ├── 否 → 停在 pending，等下一笔信号重试
          │
          └── 是
                ↓
           TqSdk 调仓到目标手数
                ↓
           确认持仓到位
                ↓
           保存执行结果
```

---

## 5. 交易信号

客户端从服务器获取：

```text
signal_id
symbol
direction
position
created_at
```

客户端必须使用 `signal_id` 判断信号是否已经处理。

---

## 6. 交易执行

服务器只告诉客户端**目标仓位**，不提供成交价格。

实际成交价格由客户端通过 TqSdk 的 `TargetPosTask`（ACTIVE 追价）在市场上撮合得到，
信号里的 `price` 只作为参考，不作为下单价格。

因此：

```text
Server
→ 决定目标仓位（做多 / 做空 / 手数）

Client
→ 把主连换成可下单的实际合约
→ TargetPosTask 追价调仓
→ 等持仓到位
```

交易成功的判定是**持仓到位**，不是「下单指令已发出」。`TargetPosTask` 只在每次
`wait_update` 时推进一步（报单、追价、撤单重下），单次 `wait_update` 不代表成交；
超时或出现本次新产生的错单即判失败，并撤掉本次未成交委托，避免界面显示失败而
账户后来成交。

---

## 7. 信号执行规则

### 新信号

收到新信号后：

1. 查询 SQLite。
2. 判断 `signal_id` 是否已经执行。
3. 如果已经执行，直接忽略。
4. 如果没有执行，检查该品种当前是否在交易时段（拿不到时段表则放行）。
5. 非交易时段则停在 pending，不执行也不记失败。
6. 在交易时段内，通过 TqSdk 把持仓调到目标手数，并等待持仓到位。
7. 记录执行结果。失败的下次同一信号重投时可以重试。

---

## 8. 防止重复交易

这是客户端最重要的业务约束之一。

同一个：

```text
signal_id
```

只能执行一次。

即使出现以下情况，也不能重复下单：

* 服务器重复通知
* 客户端重复收到通知
* 客户端重启
* 网络断开后重新连接
* 客户端重新查询历史信号

SQLite 中必须能够明确记录：

```text
signal_id
execution_status
executed_at
```

---

## 9. 仓位处理

客户端根据服务器的目标仓位执行交易。

例如：

```text
服务器 → 目标仓位 +2
客户端 → 读当前持仓
        → TargetPosTask 调仓到 +2 手
        → 等持仓到位
```

客户端不得自行改变服务器的目标仓位。

实际仓位处理逻辑应与 TqSdk 当前账户状态保持一致：调仓前的持仓、本次新产生的
委托、以及调仓后的实际持仓都从 TqSdk 会话读取，不使用本地推算值。

---

## 10. SQLite

SQLite 用于记录两类数据。

**信号执行状态**：

* 服务器交易信号
* 信号获取时间
* 信号执行状态
* 实际执行时间
* 执行结果
* 错误信息

建议至少区分：

```text
pending
executing
success
failed
```

具体状态可以根据实际代码调整。

**历史成交**（`trade_history` 表）：

* 后端常驻的账户监听会话把 TqSdk 当日成交幂等写入本地库
* 用以在跨交易日后仍能追溯（TqSdk 本身只提供当前交易日成交）
* 支持按「全部日期 / 1 年 / 30 天 / 今日」时间切片查询

---

## 11. 网络异常

客户端必须能够处理：

* Server 不可访问
* 网络断开
* Server 重启
* 通知连接断开
* API 请求超时
* 重复通知
* 获取信号失败

网络异常不能导致客户端交易状态数据库损坏。

Server 恢复后，客户端应该能够重新连接并查询未处理信号。

---

## 12. TqSdk 异常

需要处理：

* TqSdk 连接失败（`TqConnectionError`）
* 快期权限账户认证失败（`TqAuthError`）
* 交易网关不可达（启动前预探测拦截，不等 60 秒兜底）
* 行情/时段表未就绪（放行，由成交确认与超时兜底）
* 调仓超时未成交
* 委托被拒（只看本次调仓新产生的委托）
* 撤单失败
* 账户状态异常
* 网络异常
* TqSdk 重连（账户监听会话断线后 15 秒重试）

交易失败必须记录原因，并撤回本次未成交委托。

不能因为一次交易异常导致整个客户端无提示退出。

---

## 13. 数据一致性

交易执行必须尽量保证：

```text
收到信号
   ↓
记录信号
   ↓
检查是否执行
   ↓
执行交易
   ↓
确认执行结果
   ↓
更新 SQLite
```

必须避免：

```text
已经下单
但是客户端认为没有执行
↓
重新启动
↓
再次下单
```

这是客户端需要重点防止的异常场景。

---

## 14. 客户端启动

界面点「自动交易」开启后，后端按阶段推进（阶段进度通过 `engine_start_progress` 上报）：

1. **server**：校验服务器连通。
2. **accounts**：校验目标账户字段齐全（品种、策略必选）与本地 token 可用。
3. **tqsdk**：逐个账户做 TqApi 握手——`TqAuth` 登录快期权限账户 + 建账户对象（
   TqKq / TqAccount），并在建连前对交易网关做一次带认证头的预探测（避免等
   tqsdk 自己 60 秒兜底）。没有可握手的凭据时跳过本阶段。
4. **engines**：为每个账户启动信号流与执行会话。
5. 进入正常运行状态。

任一步失败即中止本次启动并返回问题清单，不会「部分启动」后静默运行。

`pct` 按各阶段经验权重折算到整次启动，且在阶段内的真实进度节点之间按
1%/秒 缓慢推进——天勤握手这类一项就要几十秒的阶段只有首尾两个真实事件，
若如实报数，顶栏胶囊会长时间停住不动，用户会以为卡死。爬行只推进到
下一个真实节点为止；预检被拦时停在拦截点，不会假装走完。

客户端重启后必须能够恢复之前的执行状态。

---

## 15. 运行模式

客户端属于长期运行程序。

正常情况下：

```text
启动
 ↓
连接 Server
 ↓
收到信号
 ↓
检查交易时段 / 读当前持仓
 ↓
TqSdk 调仓并确认持仓到位
 ↓
继续等待
```

账户数据的监听会话由后端启动时即为每个已配置账户建立，与自动交易开关无关：
不开自动交易也能看资金、持仓、委托、成交。

交易信号不是高频事件，因此不需要设计复杂的高并发交易架构。

客户端最终支持：

* macOS `.app`

## 18. 日志

至少记录：

* 客户端启动
* Server 连接
* Server 断开
* TqSdk 连接
* 发送给执行器的 `engine.start` 启动阶段（server / accounts / tqsdk / engines）
* 账户监听会话的连接与断线重试
* 收到交易信号
* 信号是否已经执行
* 调仓操作（目标仓位、实际合约）
* 调仓结果（持仓到位 / 超时 / 拒单）
* 当前仓位
* 异常
* 重连

日志需要能够还原：

> 为什么这个交易信号最终产生了这笔交易。

## 21. 开发原则

1. 不在客户端复制服务器策略。
2. 不自行判断交易方向。
3. 不随意修改交易执行逻辑。
4. 同一个 `signal_id` 不得重复执行。
5. 交易执行状态必须持久化。
6. 优先保证交易状态一致性。
7. 优先使用简单可靠的架构。
8. 不为了低频交易场景引入复杂消息队列。
9. 保持 macOS / Windows 兼容。
10. 修改交易逻辑后必须验证。
11. 不确定业务规则时不要自行假设。
